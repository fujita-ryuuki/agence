# 02 要件定義書 — 機能要件（Functional Requirements）

版：v1.0-draft｜2026-09-07｜対象：Claude Code が実装単位として読む
書式：FR-ID／ユーザーストーリー／受け入れ基準（Given-When-Then）／実装メモ。【仮置き】は 11 決定管理表 で管理。

## 0. ロールと権限

| ロール | 説明 | できること |
|---|---|---|
| expert | 専門家。自分のワークスペース（Vault）のみ | A/B/C 全機能（自分のデータのみ）、根拠表示の閲覧 |
| reviewer | ブラインド評価者。担当専門家1名に紐づく | ブラインド比較画面のみ。回答の出所・ノート・元データは見えない |
| operator | 運用者（Maxeff/PdM） | 全専門家のデータ閲覧、アカウント開設、Batch締め・再生成、Vault閲覧、ジョブ・コスト・指標閲覧、上限設定 |

認証：メールのMagic Link（Supabase Auth）。セルフサインアップ無し。operator が招待メールを送る。

## 1. 【A】Input

### FR-A1 専門領域の選択
ストーリー：専門家として、自分の専門領域を選び補足したい。疑似相談が領域に沿って生成されるようにするため。
- Given 領域マスタ（`domains`）が存在する When 専門家が複数選択＋自由記述（最大500字）を保存する Then `expert_profiles.domain_ids` と `domain_note` に保存され、以後の疑似相談生成プロンプトに反映される。
- Given 領域を保存済み When 疑似相談を生成する Then 生成された相談に `domain_id` が付き、画面で「どの領域向けか」を確認できる。
- 【仮置き】領域マスタは operator が管理画面で追加・編集する。初期マスタは参加専門家確定後に作成（論点#1）。

### FR-A2 データの投入・接続（7形式）
ストーリー：専門家として、自分が持つ資料・チャネルを任意に選んで投入したい。

共通
- 投入単位は `sources`（1ファイル・1接続範囲＝1 source）。状態：`queued → processing → ready | failed`。
- 失敗した source は理由（`error_message`）付きで一覧表示され、再試行・削除ができる。
- 投入一覧は形式・件数・抽出文字数・状態・Batch 番号を表示し、個別削除できる（削除時は派生した chunks/notes の出典参照を `orphaned` にマークする）。
- 形式ごとにON/OFF（`expert_settings.enabled_source_types`）。OFFの形式はUIで非表示。
- 取込時に「匿名化する／しない」を選択できる（FR-A2-PII）。

PDF・PPT・テキスト・Excel（ファイルアップロード）
- 対応拡張子：pdf / pptx / txt, md / xlsx, csv。上限 50MB/ファイル【仮置き】。
- PDF：テキスト抽出（画像PDFはOCR【仮置き：PoCでは未対応、失敗理由「画像PDF」を表示】）。
- PPTX：スライド単位でテキスト＋ノートを抽出、スライド番号を保持。
- Excel/CSV：シート名・見出し行を保持し、行単位のMarkdownテーブルに変換。
- Then 抽出テキストが `chunks` に分割格納され、Organize の入力になる。

動画
- アップロード（mp4/mov/m4a/mp3、上限 2GB【仮置き】）またはURL指定（YouTube・Vimeo・直リンク【仮置き：yt-dlp相当で取得可能なもの】）。
- 音声抽出→文字起こし（話者分離・タイムスタンプ付き）。長尺は 10分単位に分割処理し、途中失敗時はその分割から再開できる。
- 専門家は文字起こし結果を確認・修正できる（FR-A2-TR）。修正確定後に Organize へ渡る。
- 合計時間上限：専門家1名あたり 10時間【仮置き：論点#5】。

Slack
- OAuth（Slack App: `channels:history, channels:read, groups:history, groups:read, im:history, im:read, users:read`）。トークンは暗号化保存。
- 専門家がチャンネル（公開・参加中の非公開）と期間を指定して取り込む。DMは専門家が明示的に選択した場合のみ。
- 上限：期間 12ヶ月・合計 20,000メッセージ【仮置き：論点#5】。
- 取り込みはスレッド単位で1 chunk にまとめる。

E-mail
- OAuth（Gmail API `gmail.readonly`）【仮置き：Gmail のみ。Outlook/IMAP は対象外】。
- ラベル・期間・送受信者条件を指定して取り込む。上限：期間 12ヶ月・合計 5,000通【仮置き】。
- スレッド単位で1 chunk。署名・引用返信の重複は除去する。

FR-A2-TR 文字起こし確認・修正
- Given 文字起こし完了 When 専門家が該当 source を開く Then 話者ラベル・タイムスタンプ付きセグメント一覧が表示され、テキスト編集と話者名の付け替えができる。
- 修正率（編集された文字数／総文字数）を `transcripts.edit_ratio` に記録する（非機能要件：精度計測）。

FR-A2-PII 匿名化
- 取込時に「匿名化する」を選ぶと、Organize の前に PII マスキング処理（人名・メール・電話・企業名）を通し、置換表を `pii_maps` に保存する（専門家・operator のみ閲覧可）。
- Slack・E-mail は既定で「匿名化する」ON【仮置き】。

### FR-A3 疑似相談の生成と回答
ストーリー：専門家として、自分の領域の相談に答えることで知識を Agent に渡したい。
- 生成：Batch ごとに学習用疑似相談 15件【仮置き：論点#2】を LLM が生成する。生成条件：難易度（初級/中級/上級）、相談者属性、状況の分布を operator が設定できる（`question_gen_configs`）。
- 生成元：LLM生成に加え、専門家が過去の実相談を匿名化して持ち込める（`consultations.origin = llm | imported`）【仮置き：論点#2 併用】。
- 回答：テキスト入力またはブラウザ録音。音声は文字起こし後、専門家が修正・確定する。確定で `expert_answers.status = confirmed`。
- スキップ・後回し：`status = skipped | deferred`。未回答件数をダッシュボードに表示。
- フラグ：「自分の領域ではない」「現実的でない」を付けられ、生成品質改善のために `consultations.flag` に記録。
- 時間記録：回答画面の滞在時間を `work_logs`（type=answer）に自動記録し、専門家が手動補正できる。
- 確定回答は `consultation_id` と紐づけて Organize へ渡る。

### FR-A4 Batch 管理
- Batch は operator が作成・締める（`batches.status: open → closed`）。専門家も「締め依頼」を出せる。
- Batch に紐づく：投入 sources、確定 expert_answers、B-2 修正、生成された Vault スナップショット、Agent回答（C-1）。
- 締め時に自動で Organize（差分）→ Vault スナップショット → 評価セット回答生成 → 構造化/生RAG 両系統（H3）を実行する。
- 【仮置き】Batch は運用者管理（期間区切りではなく、検証プロトコルの段階＝Batch 0〜3）。

## 2. 【B】Organize

### FR-B1 5層構造化（内部フォーマット：Obsidian Vault）
- 入力：`chunks`（source 由来）＋ 確定 `expert_answers` ＋ B-2 修正指示。
- 出力：`notes`（種別 principle / criterion / diagnostic / case / source_ref の5層）。各 note は Markdown 本文・確信度（0〜1）・出典参照（`note_sources`: chunk_id または expert_answer_id、必須）を持つ。
- Vault：Batch 締め時に `notes` を Obsidian Vault 形式（Markdown＋`[[wikilink]]`＋YAML frontmatter）に書き出し、`vault_snapshots`（Storage 上の zip＋manifest）として保存する。専門家ごとに独立。
- 追跡：任意の note から、どの投入データ・疑似相談に基づくかを辿れる。
- 構造は 07 Organize仕様 に定義。5層標準＋領域ごとの層名称・追加を許容【仮置き：論点#3】。

### FR-B2 Web UI での確認・修正
- 一覧：層別タブ（原則／判断基準／診断フレーム／事例）、検索（全文＋タグ）、確信度フィルタ、「要確認」フィルタ（確信度 < 0.6【仮置き】）。
- 詳細：意味単位で整形した表示（見出し・本文・関連ノート・出典）。Markdown 記法・ファイル構造は表示しない。
- 操作：「正しい」「修正が必要（修正テキスト入力）」「削除」を指示 → `note_reviews` に記録。修正は次回 Organize で反映（`notes.review_status`）。
- 【仮置き】確認必須は確信度低ノートのみ。全件確認は任意。
- operator は Vault（生 Markdown）を管理画面で閲覧できる。

### FR-B3 矛盾・重複・出典不明の検知
- Organize 実行時に、新規 note と既存 note の間で（a）同条件で異なる判断基準、（b）意味重複（埋め込み類似度 > 0.92【仮置き】かつ LLM 判定）、（c）出典参照が特定できない、を検知し `conflicts` に登録する。
- 専門家は UI で「Aを正とする／Bを正とする／両方残す（条件を追記）」を選択。選択結果は次回 Organize に反映。
- 未解決 conflicts 件数をダッシュボードに表示。

### FR-B4 形式別の整理方針
- Slack・E-mail・動画：「専門家の判断が表れている箇所」を優先抽出し、雑談・事務連絡は除外。抽出／除外の判定と理由を `chunks.extraction_decision` に記録し、専門家が UI で確認・反転できる。
- 初期方針は 07 に定義。

## 3. 【C】Output

### FR-C1 Batch ごとの Agent 回答生成
- 評価用セット（`eval_set`、固定 25件【仮置き】、学習用と完全分離）に対し、Batch 締め時に自動で回答を生成する（`agent_answers`）。
- 2系統生成：`pipeline = structured`（Vault 5層検索）と `pipeline = raw_rag`（chunks 直接検索）【H3 用】。専門家 UI には既定で structured を表示、operator は両方見られる。
- 各回答に生成メタ（モデル、プロンプトバージョン、Vault スナップショット ID、参照 note ID、所要時間、コスト）を保存。
- 横並び：同一相談に対する Batch 0〜N の回答を横並び表示。operator は手動再生成できる。

### FR-C2 評価入力
- 回答単位で 5段階スコア（必須）、減点理由タグ（スコア≤3 で必須・複数選択）、自由コメント、「自分ならこう答える」（任意）。
- 「自分ならこう答える」の用途は【仮置き：論点#9】学習には使わず、ブラインド比較（C-5）の本人回答としてのみ使う（評価セットのリーク防止）。
- 進捗：未評価件数と評価完了率を表示。評価時間を `work_logs`（type=evaluate）に記録。

### FR-C3 レベルの可視化
- Batch 推移：平均スコア、合格率、スコア分布、減点タグ分布（折れ線・積み上げ棒）。
- 投入との対応：各 Batch の投入形式・件数・文字数・回答件数を同じ時間軸に表示。
- ブラインド比較結果（勝率）を表示。
- 専門家向け表示【仮置き】：点数（平均）＋到達度バー（目標 4.0 に対する %）。operator は数値のまま。

### FR-C4 根拠表示
- 各 Agent 回答に、参照した note（層・タイトル・該当箇所）と、その元データ（source 名・位置／疑似相談 ID）を表示。
- 減点時に「原因ノート」を選び、そのノートの B-2 修正画面へ直接遷移できる。
- 表示は expert・operator のみ。reviewer には表示しない（RLS で制御）。

### FR-C5 ブラインド比較
- reviewer は担当専門家の評価セットについて、本人回答と Agent 回答を A/B としてランダムに割り当てた状態で閲覧し、「A優／同等／B優」と理由を入力する。
- 割り当ては `blind_pairs` に保存し、どちらが Agent かは reviewer に見せない。集計は C-3 に反映。
- 対象 Batch は operator が指定（既定：最終 Batch）。

## 4. 運用・管理（operator）
- 専門家・reviewer アカウントの招待・停止。
- Batch の作成・締め・再生成、評価セット・学習用セットの生成と品質確認（編集・差し替え）。
- ジョブ一覧（種別・状態・所要時間・コスト・入出力サイズ）、失敗ジョブの再実行。
- コストダッシュボード（LLM トークン、文字起こし分数、埋め込み）を専門家別・Batch 別に表示。
- 取込上限の設定（形式別）。
- PoC 終了処理：専門家の指示で OAuth トークン失効、データ削除（論理削除→30日後物理削除【仮置き】）。
