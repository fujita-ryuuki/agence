# 01 要求定義書 — Agence Agent Builder PoC（v1.0-draft）

版：v1.0-draft（v0.2キックオフ資料を再構成）｜日付：2026-09-07｜作成：PdM（AI生成・レビュー前）
凡例：【確定】社長判断済み／【仮置き】PdM推奨案で仮採用（論点DBで決着後に差し替え）／【対象外】PoCでは作らない

## 1. 事業と PoC の位置づけ

| 項目 | 内容 |
|---|---|
| 事業 | 専門家が自身の知識を詰めた外部脳/Agentを販売するマーケットプレイス。購入者はMCP経由で自身のLLMに接続、またはAgence Nativeアプリのチャットで専門家Agentに相談する |
| PoC対象 | Agent Builder（専門家がAgentを作る側）のみ |
| PoCの問い | 専門家がAgent Builderで作ったAgentは、専門領域の相談に対して「専門家本人が納得する回答」を出せるか。出せないなら何を追加・改善すれば出せるか |
| 成功の定義 | 固定の評価用疑似相談セットに対し、Batch最終時点で平均スコア4.0以上、合格率（スコア4以上）70%以上、スコア1比率5%未満。専門家の投入時間が事業として現実的な範囲に収まること |
| 専門家の操作面 | Web UIのみ【確定】。Obsidianは内部フォーマットに留め、専門家には露出しない |
| 投入データ | PDF・PPT・動画・テキスト・Excel・Slack・E-mail の7形式【確定】。どれを接続するかは専門家本人が選ぶ |

## 2. 上位制約（事業前提から引き継ぐ設計制約）

1. 売買対象は「Agent利用権」。Agentは専門家不在でも自律的に一定水準の回答を出す必要がある。
2. 購入者はMCP接続で知識にアクセスする。Agent Builderの出力物は将来「MCPサーバーとして配信可能なパッケージ」に変換できる構造にする（PoCでは配信しない）。
3. MCP経由・Nativeアプリ経由で同一Agentが同一水準の回答を返すよう、知識と回答ロジックはクライアント非依存で保持する。
4. 知識の中身（元データ・整理済みノート）は購入者が直接閲覧できない構成にする。PoCでは根拠・出典の表示を専門家本人と運用者に限定する。
5. 購入者の相談ログを知識改善へ還流させる。PoCの「疑似相談→本人回答→再整理→再回答」ループは将来この還流ループにそのまま置き換わる設計にする。

## 3. 検証仮説

| ID | 仮説 | 切り分け方法 |
|---|---|---|
| H1（主） | 既存資料の投入・接続と疑似相談への回答を行えば、専門家本人が「自分の回答として出して良い」と判断する回答をAgentが出せる | Batch最終の主指標が目標値を満たすか |
| H2 | 既存ドキュメントのみでは納得度が頭打ちになり、疑似相談への本人回答を加えると有意に上昇する | Batch0（既存データのみ）とBatch1以降の差 |
| H3 | 5層構造化Vault経由の回答は、生ドキュメントを直接検索するRAG構成より納得度が高い | 同一投入データで「構造化」「生RAG」の2系統を同一評価セットで比較 |
| H4 | Batchを重ねるほど納得度が単調に上がり、収束点が見える | Batch推移の平均スコア |
| H5 | 専門家1人あたり現実的な作業時間（PoC全体10〜15時間【仮置き】）の範囲で目標水準に到達できる | 作業種別ごとの時間記録と到達スコアの対比 |
| H6 | データ形式によって納得度への寄与が異なる | 接続形式の組み合わせと納得度・減点タグの相関 |

## 4. 「専門家本人が納得する回答」の操作的定義【確定】

| 指標 | 定義 | 目標値 |
|---|---|---|
| 納得度スコア（主） | 評価用疑似相談1件ごとに専門家が5段階評価。5=そのまま出せる／4=軽微な修正で出せる／3=修正すれば出せる／2=方向性は合うが出せない／1=誤り・有害 | Batch最終で平均4.0以上、スコア1比率5%未満 |
| 合格率（主） | 評価用セット全件のうちスコア4以上の比率 | 70%以上 |
| 減点理由タグ（分析用） | スコア3以下に対し複数選択。①事実・数値の誤り／②原則・判断基準の取り違え／③文脈・前提条件の不足／④表現・トーンの不一致／⑤判断の踏み込み不足／⑥その他（自由記述） | 目標値なし |
| ブラインド比較（補助） | 本人回答とAgent回答を伏せ、同領域の別専門家が優劣判定 | Agent勝率（同等含む）40%以上 |
| 投入コスト（事業判断用） | 専門家の作業時間を「アップロード・接続／疑似相談回答／整理結果確認／評価」別に記録 | 目標値なし（H5の判断材料） |

評価用疑似相談セットは学習用と分離し、PoC期間中は固定する。

## 5. スコープ

### In Scope
- 【A】Input：専門領域の選択／7形式の投入・接続／疑似相談の自動生成と専門家回答（テキスト・音声）／Batch管理
- 【B】Organize：投入データの5層構造化（内部フォーマット：Obsidian Vault）／Web UIでの確認・修正／矛盾・重複・出典不明の検知／形式別抽出方針
- 【C】Output：Batch単位のAgent回答生成・横並び閲覧／評価入力／レベル推移の可視化／根拠表示／ブラインド比較画面
- 運用：専門家アカウント（手動開設）、Batch管理、指標集計、ジョブ・コストのログ
- Slack・E-mailのOAuth連携と取込範囲指定、動画の文字起こし、個人情報の匿名化

### Out of Scope【対象外】
- 購入者向け機能全般（マーケットプレイス、検索、課金・決済、MCP配信、Nativeアプリチャット）
- 購入者の相談ログ還流ループ
- 専門家によるObsidianの直接操作
- 本番水準のマルチテナント・SLA・スケーラビリティ、一般公開・セルフサインアップ、価格設定・パッケージング

### 対象ユーザー

| ユーザー | 人数 | 役割 |
|---|---|---|
| 専門家（expert） | 3〜5名【仮置き：論点#1】 | 領域選択、データ投入・接続、疑似相談回答、整理結果確認、Agent回答評価 |
| ブラインド評価者（reviewer） | 専門家1名あたり1名【仮置き：論点#6】 | 本人回答とAgent回答を伏せた状態で優劣判定 |
| 検証運用者（operator） | 1〜2名 | Batch設計、疑似相談セット品質確認、指標集計、専門家サポート、Organize監視、Vault閲覧 |

## 6. 機能要求一覧（要件定義 02 へ展開）

| ID | 要求 | 決定状況 |
|---|---|---|
| A-1 | 専門家が専門領域を選択できる（マスタ複数選択＋自由記述） | 領域マスタ粒度は【仮置き：論点#1に付随】 |
| A-2 | 7形式のデータを投入・接続できる。形式ごとにON/OFF、失敗一覧、投入一覧、個別削除 | 【確定】形式・任意接続／取込上限は【仮置き：論点#5】 |
| A-3 | 疑似相談を自動生成し、専門家がテキスト・音声で回答できる。スキップ・フラグ・未回答把握 | 生成元・件数・時間上限は【仮置き：論点#2】 |
| A-4 | 投入はBatch単位で管理し、締めは明示的に行う | Batch定義は【仮置き】運用者管理 |
| B-1 | 投入データを5層（原則／判断基準・数値ライン／診断フレーム／事例／出典）のノート群に構造化。専門家ごとに独立Vault | 【確定】Obsidian内部化／5層標準は【仮置き：論点#3】 |
| B-2 | 整理結果をWeb UIで一覧・検索・閲覧し、正しい／修正／削除を指示できる。Markdown記法は見せない | 確認範囲は【仮置き】確信度低のみ必須 |
| B-3 | 矛盾・重複・出典不明を検知し、専門家がどちらを正とするか選べる | 【仮置き】PoC必須に含める |
| B-4 | 会話的データ（Slack・E-mail・動画）から判断が表れている箇所を優先抽出し、除外判断を専門家が確認できる | 抽出方針は 07 で初期設定 |
| C-1 | Batchごとに固定評価セットへのAgent回答を生成し、Batch横並びで閲覧できる。締め時自動＋手動再生成 | 件数は【仮置き】25件 |
| C-2 | 回答ごとに5段階スコア・減点タグ・コメント・「自分ならこう答える」を入力できる | 【確定】指標／「自分ならこう答える」の用途は【仮置き：論点#9】 |
| C-3 | Batch推移の平均・合格率・分布・減点分布・投入形式との対応・ブラインド結果をグラフ表示 | レベル表現は【仮置き】点数＋到達度バー |
| C-4 | 回答に参照ノートと元データへの参照を付け、ノート修正へ直接遷移できる | 【確定】表示は専門家・運用者限定 |
| C-5 | ブラインド評価者向けの伏せ比較画面（A優／同等／B優＋理由） | 評価者確保は【仮置き：論点#6】 |

## 7. 非機能要求（PoC水準）
09 非機能要件・セキュリティ に展開。要点：専門家間の完全なデータ分離、知識層と回答生成層の分離、Obsidianのサーバー側内部化、文字起こし精度・コストの記録、生成の再現性（モデル・プロンプト・Vaultバージョン記録）、処理ログの可観測性、手動運用の許容、取込時の匿名化選択。

## 8. 検証プロトコル

| 段階 | 期間 | 内容 |
|---|---|---|
| 準備 | 2週 | 専門家確定・領域選択、評価用セット（固定25件）と学習用セット（各Batch 15件）生成・品質確認、ブラインド評価者確保 |
| Batch 0 | — | 既存データのみ投入→Organize→評価セット回答→専門家評価（H2ベースライン、接続形式を記録=H6） |
| Batch 1〜3 | 各2週 | 学習用疑似相談に回答→再Organize→再回答→評価。B-2修正を反映。作業時間を記録（H5） |
| 比較分析 | 1週 | Batch推移（H4）、構造化 vs 生RAG（H3）、減点タグ分布、ブラインド比較 |
| 判定 | — | Go（招待制β）／Pivot（再PoC）／Stop |

想定期間：約3ヶ月（準備2週＋Batch運用6〜8週＋分析1週）。
