# 05 システムアーキテクチャ・技術選定

版：v1.0-draft｜2026-09-07｜制約：なし（社長回答 2026-09-07）。以下はすべて【仮置き】。選定理由と代替案を併記。

## 1. 全体構成

```
[Browser] ── Next.js 15 (App Router, TS, Tailwind, shadcn/ui) ── Supabase (Postgres+pgvector, Auth, Storage, RLS)
                         │                                              ▲
                         │ enqueue (jobs table)                          │ read/write
                         ▼                                              │
                  [Worker: Node/TS, pg-boss] ──► 外部 API: Claude API / Embeddings / 文字起こし / Slack / Gmail
                         │
                         └──► Vault Export (Obsidian 形式 zip → Storage)
```

- Web と Worker は同一モノレポ（`apps/web`, `apps/worker`, `packages/core`）。
- Worker は Postgres をキューにする（pg-boss）。外部キュー（Redis 等）を持たない＝PoC の運用を単純化。
- LLM 呼び出しは `packages/core/llm` に集約し、プロンプトは `packages/core/prompts/*.md` にバージョン付きで保持（gen_meta.prompt_version に記録）。

## 2. 技術選定

| 領域 | 選定【仮置き】 | 理由 | 代替案 |
|---|---|---|---|
| フロント/BFF | Next.js 15 + TypeScript + Tailwind + shadcn/ui | Claude Design→Claude Code の生成互換性が高い。Server Actions で BFF を薄く保てる | Remix / SvelteKit |
| DB/Auth/Storage | Supabase（東京リージョン） | Postgres + pgvector + RLS + Auth + Storage を一体で持てる。専門家分離を RLS で実現 | Neon + Clerk + S3 |
| ジョブ | pg-boss（Node worker） | 依存を増やさず再試行・スケジュールが可能 | Inngest / Trigger.dev |
| LLM（整理・回答） | Claude API：Organize・回答生成は claude-sonnet-5、大量抽出・分類は claude-haiku-4-5 | 長文構造化と日本語品質。コスト層別 | OpenAI GPT 系 |
| 埋め込み | OpenAI text-embedding-3-small（1536次元） | 日本語で実績、安価 | Voyage AI voyage-3 |
| 文字起こし | Deepgram（nova 系、diarization ON、ja） | 話者分離＋タイムスタンプを API 一発で取得 | AssemblyAI／Whisper API＋pyannote（話者分離を自前化） |
| 動画取得 | yt-dlp（Worker 内）＋ ffmpeg で音声抽出 | URL 指定要件のため | サーバー側アップロードのみに限定 |
| ファイル抽出 | pdf-parse（PDF）、officeparser/pptx 解析（PPTX）、SheetJS（Excel）、csv-parse | Node で完結 | unstructured.io（OCR 込み・別サービス） |
| PII 匿名化 | LLM（haiku）によるエンティティ抽出＋辞書置換 | 日本語人名・企業名に強い | 正規表現のみ（精度不足） |
| OAuth | Slack OAuth v2 / Google OAuth（gmail.readonly） | 要件どおり | — |
| ホスティング | Vercel（web）＋ Fly.io or Railway（worker） | 手軽。Worker は長時間ジョブのため常駐 | 全部 Fly.io |
| 可観測性 | jobs/cost_logs テーブル＋ Sentry | 要件の「入出力・所要・コスト」を DB に残す | Langfuse（LLM トレース） |

失敗シナリオ（推奨案の反証）
- Deepgram の日本語話者分離精度が低い場合：AssemblyAI へ切替（アダプタ層 `packages/core/transcribe` で差し替え可能にしておく）。
- pgvector の検索性能が chunks 数十万件で劣化：PoC 規模（専門家5名×数万 chunk）では想定内。超える場合は HNSW インデックスへ変更。
- Vercel の関数タイムアウト：LLM 呼び出しは全て Worker 側で行い、Web は enqueue と閲覧のみにする。

## 3. 主要パイプライン

### 3.1 取込（Ingest）
1. `sources` 作成（queued）→ job `extract`（ファイル）／`import_slack`／`import_email`／`transcribe`（動画）
2. 抽出テキストを chunk 化（見出し・スライド・スレッド境界を優先、最大 1,200 トークン、オーバーラップ 100）
3. `anonymize=true` なら job `anonymize`（chunk 単位、pii_maps 保存）
4. B-4 抽出判定（会話系のみ）：haiku で「判断が表れているか」を分類、`extraction_decision` を記録
5. job `embed` → chunks.embedding
6. `sources.status = ready`

### 3.2 Organize（Batch 締め時・差分）
1. 対象：前回 Organize 以降に ready になった chunks（kept のみ）＋ confirmed expert_answers ＋ 未適用 note_reviews ＋ 解決済 conflicts
2. 抽出：sonnet で chunk 群から候補ノート（層・タイトル・本文・出典抜粋・確信度）を生成（07 のプロンプト）
3. 統合：既存 notes と埋め込み類似検索→「更新／新規／重複候補」を判定。note_reviews の fix_text を反映、delete は review_status=deleted
4. リンク：note_links を生成（原則⇄判断基準⇄診断フレーム⇄事例）
5. 矛盾検知：類似 criterion 同士を sonnet で比較→ conflicts 登録
6. Vault 書き出し：07 の Vault 形式で zip → Storage → vault_snapshots
7. 評価セット回答生成（3.3）を structured / raw_rag の両系統で実行

### 3.3 回答生成（Answer）
- structured：質問埋め込み→ notes（principle/criterion/diagnostic 優先、case 補助）を top-k 取得→ 診断フレームに沿って回答。cited_note_ids を返す
- raw_rag：質問埋め込み→ chunks top-k → 回答。cited_chunk_ids を返す
- 両方とも gen_meta に model / prompt_version / vault_snapshot_id / tokens / cost / latency を保存
- 再現性：同一 batch・consultation で再生成すると `regenerated_from` を持つ新行を作る（上書きしない）

### 3.4 疑似相談生成
- 入力：domain、domain_note、difficulty 分布、persona 分布、既存相談（重複回避）
- 出力：consultations（origin=llm）。評価用セットは eval_sets を locked にした後は生成・変更不可

## 4. MCP 配信を見据えた分離
- 知識層：`notes` + `vault_snapshots`（Vault は将来 MCP サーバーの知識パッケージそのもの）
- 回答生成層：`packages/core/answer`（入力：質問＋Vault スナップショット ID、出力：回答＋引用）。Web/Worker どちらからも同じ関数を呼ぶ＝クライアント非依存
- 購入者に出すのは回答のみ。引用（cited_*）の表示は UI 側で expert/operator のみに限定し、API 層でも reviewer/購入者ロールには返さない
